# Proposed issue (DRAFT -- not filed; requires user authorization)

## Title
Add downcast edges to navigation graph so ILexSense -> IFsSymFeatVal resolves

## Body

### Problem

`find_navigation_path` (get_navigation_path tool) cannot find a path from
`ILexSense` to `IFsSymFeatVal`, even though one exists in the live LCM
object model. The path runs through `MsFeaturesOA`, but that property
lives on the concrete class `IMoStemMsa`, not on the base interface
`IMoMorphSynAnalysis` that the navigation graph walks. Because the graph
is built from declared members of the base type, the edge is invisible
to BFS and the query correctly, but unhelpfully, returns `found: false`.

This was surfaced as a known limitation during the #85/#88 BFS fix
(`d693e26`) and the #86 inheritance-resolution work (`13f69f8`) and
deliberately deferred rather than folded into either, since fixing it
touches the shipped navigation-graph data artifact rather than the
query/pagination code.

### Proposed scope (CP3)

1. **Add `required_cast`-labeled downcast edges** to the navigation graph
   schema, so an edge can declare "traverse this property, but only after
   downcasting the source node to concrete subtype X." This models real
   FieldWorks patterns like `IMoMorphSynAnalysis` -> `IMoStemMsa` ->
   `MsFeaturesOA` -> `IFsFeatStruc`.

2. **Decide the subtype-selection policy.** A base interface can have
   multiple concrete subtypes that each expose a different downstream
   edge. Critically, the MSA siblings do not merely differ by type --
   they do not share the property *name* at all (established by the
   cycle-1 domain review against `casting_index_liblcm-v11.0.0.json`):

   | Subtype | Feature property |
   |---|---|
   | `IMoStemMsa` | `MsFeaturesOA` |
   | `IMoInflAffMsa` | `InflFeatsOA` |
   | `IMoDerivAffMsa` | `FromMsFeaturesOA` / `ToMsFeaturesOA` |
   | `IMoUnclassifiedAffixMsa` | *(none)* |

   So naive edge generation is actively unsafe: if subtypes are ordered
   alphabetically, `IMoDerivAffMsa` wins the BFS and emits code
   referencing a property that does not exist on that class -- or
   silently yields `None` under a `getattr` default. The domain review's
   judgement was that **a wrong-subtype path is worse than no path**,
   because a linguist without an engineering background has no
   independent way to catch it before it corrupts a batch report.
   Stem/root entries vastly outnumber affixal ones, so `IMoStemMsa` is
   the statistically correct default if a single primary is chosen.

   Need a policy for:
   - whether to enumerate all viable subtypes and return multiple
     candidate paths, each labeled with its `required_cast`, or
   - pick one "primary" subtype per base type and document the rest as
     unreachable-by-default, or
   - some hybrid keyed off runtime type inspection where possible.
   This decision should probably live alongside DEC-2 (interface-only
   scoping) as a new decision record.

3. **Regenerate `navigation_graph_liblcm-v11.0.0.json`** via
   `src/flextoolsmcp/build_navigation_graph.py` once the schema and policy
   are settled, and verify the `ILexSense -> IFsSymFeatVal` case resolves
   end-to-end via `server.call_tool`.

### Why its own issue, not folded into #86

#86 is scoped to query/pagination behavior over the *existing* graph
data (`get_object_api`, `resolve_property`). CP3 requires changing what
the graph itself contains -- a shipped data artifact regenerated by
`build_navigation_graph.py` -- plus a design decision about
subtype-selection semantics that has no clear default. Mixing the two
would make #86 harder to review and land, and blocks it on an open
design question it doesn't otherwise depend on.

It's also not something #86's mechanism could ever close: `MsFeaturesOA`
is declared on the concrete subtype `IMoStemMsa`, not on any ancestor
interface, while `collect_inherited_members()` (added by #86 in
`13f69f8`) only walks ancestors upward via `interfaces` union
`base_classes`. An upward ancestor walk can never surface a member
declared on a descendant, so #86's merge does not, and structurally
cannot, address this case -- it needs a downcast edge, which is a
different mechanism entirely.

### Motivating case

`ILexSense -> IFsSymFeatVal`: unreachable today because `MsFeaturesOA`
is declared on concrete `IMoStemMsa`, not on the base
`IMoMorphSynAnalysis` the graph walks. Confirmed still returning
`found: false` (correctly, given current graph data) as of the #85/#88
fix landing in `d693e26`.
