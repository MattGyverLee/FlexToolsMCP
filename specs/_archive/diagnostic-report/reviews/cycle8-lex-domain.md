## Item 1 — Sensitivity-by-shape (section 9, resolved Q4): PASS

`src/flextoolsmcp/server/diagnostic/sensitivity.py:60-143` (`_LexicalFlowVisitor`, `detect_lexical_shape`) is pure `ast`-based structural analysis: it walks `ast.Call`/`ast.Attribute`/`ast.Assign`/`ast.Constant` nodes, matching lexical-accessor call/attribute *names* (`GetGloss`, `GetDefinition`, `GetLexemeForm`, `.BestVernacularAlternative`, `.BestAnalysisAlternative`, `.Text`) and a BCP-47 regex (`_BCP47_RE`, sensitivity.py:57) applied only to a string literal's *shape* (`^[a-z]{2,3}(-[A-Za-z0-9]{2,8}){0,3}$`), never to lexical values. `likely_contains_lexical_data()` (sensitivity.py:146-164) only ever reads `op.log_lines`' extracted `Code:` block text — never `report.Info`/`report.Error` runtime output — so detection cannot read or leak the data it's flagging about. `detect_lexical_shape` fails closed on `SyntaxError`/`ValueError` (never raises).

Confirmed the flag drives only email-vs-GitHub framing and touches nothing else: `prepare_report_bundle()` (diagnostic_report.py:221) computes `likely_lexical` and returns it as a plain informational key (`likely_contains_lexical_data`) alongside the bundle; it is never read by `render.render_report()` (render.py has zero references to `sensitivity`/`likely_lexical`) and never read by `transports.build_transports()` (transports.py:212-241 always builds `gh` + `github_url` + `mailto` unconditionally — no branch on the flag). GitHub stays the structural default and "don't send" is always available regardless of the flag's value; the flag is advisory text for Claude to relay, not a code-path branch.

## Item 2 — Path-scoped normalization / no document-wide replace (section 8.3, E2): PASS

`src/flextoolsmcp/server/diagnostic/normalize.py` is unchanged in spirit from CP2 and CP3's new render surfaces route through it correctly: `render.render_report()` (render.py:257-280) assembles all seven sections (including CP3's new `end_mismatches`/`rotation_truncated` blocks added to `_render_what_was_tried`, render.py:174-199) into one `body` string and applies `normalize.normalize_report_text(body)` exactly once, at the very end (render.py:280) — a single path-scoped regex pass (`_PATH_TOKEN_RE`, normalize.py:60-64), never a raw `str.replace`/`re.sub` on the username or home-path as a bare substring anywhere in the diff. Home-dir substitution requires a full-string prefix match plus a path-segment boundary check (normalize.py:117-124); username substitution requires an exact whole-segment match, never `in`/substring (normalize.py:97-112, `_replace_username_segments`). No CP3 file performs a second, independent normalization pass or a document-wide find/replace — `sensitivity.py` and `transports.py` do not call `normalize` at all (they don't need to; they don't touch report body text at the level normalize.py governs). No regression found.

One ancillary observation (not a regression, out of scope for this item's literal ask): `transports.py`'s `_short_body_text()` (transports.py:112-123) embeds the raw, un-normalized `report_path` (e.g. `C:\Users\<realname>\.flextoolsmcp\reports\report_...md`, from `offered_store.get_reports_dir()` -> `Path.home()`) directly into the GitHub-URL and mailto short bodies — the only transport text that is not passed through `normalize_report_text()`. Section 8.3 scopes normalization to "file paths in report headers, tracebacks, code fingerprints, and discovery-call arguments" (i.e. the report file), so this doesn't violate the letter of the acceptance criterion, and the leaked value is just the user's own OS username in their own local file path (not lexical data) — but it is a real, if minor, path-not-normalized gap in a string that *does* leave the machine if the user completes the send. Worth a follow-up ticket, not a CP3 blocker.

## Item 3 — Never-auto-send is structural (section 8.1): PASS

Read directly from `prepare_report_bundle()` (diagnostic_report.py:159-248), not inferred from the guard tests: there is exactly one `Path.write_text()` call in the whole function (diagnostic_report.py:219, guarded by the `offer_gate` early-return at line 206-207 so a dedupe-suppressed offer never even reaches it), and the only other externally-visible action is `transports_mod.build_transports(...)` (line 226), which — confirmed in `transports.py` — never imports or calls `subprocess`, `smtplib`, `webbrowser`, an HTTP client, or a raw socket; `default_gh_available()` (transports.py:49-59) is a `shutil.which("gh")` PATH lookup, not a `gh` invocation. `handle_prepare_report()` (diagnostic_report.py:322-372) and `build_advisory_for_success_close()` (diagnostic_report.py:251-319) both terminate in a plain dict/JSON response; neither calls anything network- or process-capable. This matches the spec's framing that never-auto-send is structural, not a policy promise.

## Item 4 — Preview fidelity (section 8.2 / E4): PASS (with one caveat worth naming)

`prepare_report_bundle()`'s return dict (diagnostic_report.py:235-248) carries both `report_markdown` (the full rendered file content, line 240) and `transports` (the actual capped per-channel strings — `gh.display`/`gh.argv`, `github_url.url`/`body_text`, `mailto.uri`/`body_text` — from `transports.build_transports()`). `flextools_prepare_report`'s handler (`handle_prepare_report`, diagnostic_report.py:322-372) forwards the bundle unmodified, so the explicit tool path fully satisfies E4 end-to-end.

Caveat: `build_advisory_for_success_close()` (diagnostic_report.py:299-307) deliberately strips `report_markdown` before attaching to `RunModuleSuccess` (the report's own "Residual concerns" section flags this as intentional, to keep the payload light). So the *automatic* advisory surfaces `report_path` (a pointer) rather than the file bytes inline — the full-file half of the E4 preview is only literally present in the payload when Claude (or the user) separately opens `report_path` or calls `flextools_prepare_report` again. Given this MCP's primary client is a coding agent with local filesystem read access (not a sandboxed chatbot), this is a defensible, already-flagged trade-off rather than a hidden gap — but it means the auto-offer response by itself does not carry the "both artifacts" preview the way the explicit tool does. I'd call this PASS at the "bundle" level as the task scoped it, with the caveat on record.

## Item 5 — THE KEY JUDGMENT CALL: advisory attach point (report lines 113-133): FAIL

**Ruling: does not fully satisfy section 6.2 + section 6.5 intent — it misses the "reportably-failed-then-abandoned" case, which is arguably the single most important case the feature exists to catch.**

### What the implementation does
`build_advisory_for_success_close(op_id)` is wired into `execution.py` at exactly one call site: inside `if execution_result.get("success"):` (execution.py:3300, advisory attached at :3356-3358). It is **never called** from the `else:` branch (the `runtime_fail`/reject path, execution.py:3359-3379), which instead returns `execution_result` directly as a raw JSON dict (line 3376) with no advisory attachment attempted at all. So the advisory can only ever surface on a later, same-turn `ok` close — never on the qualifying failing close itself, and never at all if no such `ok` close ever happens.

### Why this is a real gap, not just a technicality
1. **Section 6.1 says the trigger fires "on the closing op"** — i.e. on the failing close itself (`outcome == "runtime_fail"`, `invalid_api_chain`, casting-recurrence) — not "on some later close that happens to succeed." The implementation's deferral to the next `ok` close is a reasonable *engineering* compromise given section 11 Q5's resolution that the field lives only on `RunModuleSuccess`, but that compromise has a consequence nobody in the chain explicitly signed off on: a turn that never produces a same-turn `ok` close gets no automatic offer, period.
2. **The spec explicitly anticipates this exact scenario as a legitimate, even expected, report outcome** — twice: section 5 ("...forward to the resolution so the maintainer sees the fix **(or the give-up)**") and section 7 item 6 ("...the follow-up op(s) that went green, **or a note that the turn was abandoned**"). `render._render_resolution()` (render.py:233-246) even implements this explicitly: `"Not resolved in this slice: no green (ok) close was captured -- the turn appears to have been abandoned."` The *bundle content* is fully spec-compliant for an abandoned turn — but only if a report gets prepared at all. The auto-offer's attach point structurally guarantees it never gets prepared automatically for exactly this outcome.
3. **This is precisely the scenario section 1's motivation is written around**: "Today that hand-off is entirely manual and undiscoverable... Most users never do it, so real inconsistencies... go unreported." A user who hits a `runtime_fail`/`invalid_api_chain`/casting-recurrence and then gives up (switches tasks, ends the session, or just moves on without a same-turn fix) is the *canonical* case of "a real inconsistency that would otherwise go unreported" — arguably more so than the case that already gets an offer (where the user found a workaround and moved on with a fresh `ok`, i.e. arguably less urgent to report since it self-resolved). The current wiring silently favors offering on the *less* urgent case and drops the *more* urgent one.
4. **This is not a hard technical constraint.** `error_response()` (`src/flextoolsmcp/response_utils.py:197`) builds a plain dict and accepts arbitrary `**extra` kwargs; the `runtime_fail` branch (execution.py:3374-3378) returns a raw `execution_result` dict, not a strictly-validated Pydantic model that would reject an extra key. Section 11 Q5 fixed the field's *documented home* as `RunModuleSuccess` for contract purposes, but nothing in the code prevents also attaching an (additive, undocumented-in-TOOL-CONTRACT.md, best-effort) advisory to the failing response itself, or — short of that — checking at the *start* of a new turn (`flextools_start`) whether the immediately-preceding turn closed with an un-actioned reportable failure and offering then.
5. **Test coverage confirms the gap is untested, not just unimplemented**: per cycle7's own description, the wiring test drives "two real `handle_run_module()` calls (fail then ok, same turn)" and a companion "no advisory on an all-green turn" — there is no test for "fail, then turn ends/changes intent with no `ok`," which is exactly the missing branch.

### The specific missed scenario (concrete)
A user asks Claude to do something; the op closes `runtime_fail` (reportable per section 6.1). Claude cannot find a fix, the user says "never mind, let's do something else" (a new, different `user_intent` — a new turn by section 5's grouping), and no further op in the *original* turn ever closes `ok`. Per current wiring: `build_advisory_for_success_close` is never invoked for that turn's failure (it's only invoked at a success close, and the new turn's own eventual success close belongs to a *different* `user_intent` group, so `group_records_by_intent` would not even group the two turns together). The `diagnostic_report` advisory silently never surfaces. The only recovery path is the user or Claude proactively calling `flextools_prepare_report` — which requires already knowing to ask, the exact discoverability failure mode section 1 says this feature exists to fix.

### Recommendation
Not a CP3 blocker in the sense of "revert and redo," but this should be logged as a known gap before CP3 is called done, with one of:
- (a) also attach a (best-effort, non-contract, fail-open) `diagnostic_report` key directly onto the `runtime_fail`/reject dict response at the qualifying failing close itself, so the offer can fire immediately without waiting for a resolution that may never come; or
- (b) add a "check the immediately-preceding turn for an un-offered reportable failure" hook at `flextools_start` time, so a turn-abandonment doesn't permanently suppress the auto-offer; or
- (c) explicitly accept the gap as a documented v1 limitation (update the spec/tasks.md to say so plainly) rather than leave it as an implicit, undiscussed side effect of the Q5 RunModuleSuccess-only decision.
