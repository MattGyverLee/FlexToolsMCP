# Implementation Plan: Unified recipes

**Spec**: `specs/unified-recipes/spec.md` | **Tier**: Full | **Size**: oversized
(about 35 files, about 45 tasks) | **Write path**: yes (shipped write recipes;
Sena 3 only)

Companions: `research.md` (R1..R18), `data-model.md`, `contracts/tools.md`,
`quickstart.md`, and `raw-lcm-ledger.md` (the deduplicated raw-LibLCM
rewrite and gap list, regenerated by `tools/scan_raw_lcm.py`).

## Summary

This change merges the skeleton closet and the curated recipes into one
concept, called **recipes**. A recipe is either *shipped* in the package or
*local*, captured from this user's own successful runs. Both kinds share one
shape, one ranked search, and one listing tool.

Shipped recipes gain a second, one-file-per-recipe source under
`src/flextoolsmcp/recipe_library/`. Each file has a `key: value` metadata
docstring and an MCPlayground-style `# --- PARAMS ---` block. A new
`recipe_files.py` module parses these files, and they are merged into
`CURATED_RECIPES`, so the validator gate, `extract_patterns` and the existing
consumers pick them up unchanged.

`skeleton_storage.py` is replaced by `server/local_recipes.py`. It captures the
whole snippet when `user_intent` is set, deduplicates by a comment- and
whitespace-insensitive fingerprint, and migrates the legacy
`skeletons.jsonl` once, recovering intents from `operations.jsonl`.

`search_by_capability` gains ranked `recipes` / `recipes_count` keys. The
existing `results[0].recipe` stays byte-identical, and `find_examples` adds
local recipes. A new tool, `flextools_list_recipes`, is added, and
`flextools_list_skeletons` becomes a deprecated alias. Server instructions are
added for the first time, and a `flextools-mcp-recipe promote` command closes
the promotion loop.

The first shipped batch ports at least 12 of the 16 tasks in FR-050 to
current flexicon (4.11.0). Every recipe passes the extended validator in CI and
is verified on **Sena 3**:

- read recipes are run unchanged;
- write recipes get a dry run;
- recipes that create objects also get a live write with `.fwdata` hash and
  mtime evidence.

No new dependencies are added.

## Constitution Check

Gate run before Phase 0 and again after Phase 1 design (result unchanged).

| Principle | Assessment |
|---|---|
| I. Safety-First Write Path | **PASS.** Capture writes only to `~/.flextoolsmcp/`. Every shipped write recipe must guard writes with `if modifyAllowed:` (validator, FR-041). Each one is dry-run on Sena 3, and any recipe that creates objects gets a live run with pre/post evidence (R14). Nothing gets a validator exemption (spec edge case, #278). Live writes need a human present; an unattended run stops as `needs-human`. Recipes add no new write path to the server itself: they execute through the existing `run_module` ladder. |
| II. Discovery Over Memory | **PASS.** Serving a recipe with code records its entities as validated discovery (FR-026, matching today's behaviour). Recipes are indexed building blocks. Porting uses `get_object_api` / `search_by_capability` against the 4.11.0 index, and the calls are cited in the evidence (R15). |
| III. Self-Contained Extraction | **PASS.** `extract_patterns.py` merges `CURATED_RECIPES` into `common_patterns_flexicon-v4.11.0.json`. That index is regenerated in a full refresh and committed with the change. Recipe files are parsed statically (AST and tokenize) and never executed at load. |
| IV. Append-Only Contracts | **PASS.** New keys only (`recipes`, `recipes_count`, `deprecation`) and one new tool. `results[0].recipe`, `skeletons_from_your_sessions` and `flextools_list_skeletons` stay in place, with deprecation notices naming `tool-responses/2.0`. The new error code `recipe_not_found` is appended. The CHANGELOG gets a "Tool contract" entry. A contract snapshot test pins SC-006. |
| V. Errors That Teach | **PASS.** `recipe_not_found` carries `closest_matches` and a next call. The promote CLI prints the nearest ids and explains each scrub line. A malformed recipe file logs one clear error naming the file and key. |
| VI. One Source of Truth | **PASS.** The raw-LCM gate's wrapper suggestions come from the regenerated bridge index, not a hand-kept table, and deprecation reads the index as well as the curated list. The format, the PARAMS parser and the scrub patterns live in `recipe_files.py`, shared by the loader, validator and promote. Ranking lives in `server/recipes.py` only. Entity mapping reuses `validators._accessor_to_ops_map`. There is no parallel copy of shipped recipes. The MCPlayground scripts stay upstream sources, not copies to keep in sync (their `origin` names them). |
| VII. Windows-First | **PASS.** `os.replace` handles the atomic rewrite on Windows. Console output from the CLI is ASCII only. JSONL is read and written as UTF-8 with `ensure_ascii=False`, and the CLI writes drafts as UTF-8 so vernacular text in code survives. |
| Quality gates (tests / CHANGELOG / index / golden / integrity) | **PASS, scheduled.** The Test map below covers every FR. The golden fixture for `recipe_not_found`, the regenerated `common_patterns` index, the USAGE.md row (`validate_integrity.py server`) and the CHANGELOG are all tasks. The pattern audit applies to the entity-tagging bug that FR-012 replaces (`_entities_used_in_session`); see "Pattern audit obligation". |

No violations, so no Complexity Tracking table.

**Structure decision**: The existing single-package layout is kept. The only
new top-level concepts are a data directory (`recipe_library/`) and two
modules: `recipe_files.py`, which sits beside `curated_recipes.py` so
`extract_patterns` can reach it without the server package, and
`server/local_recipes.py`, which sits where `skeleton_storage.py` was.

## Phases

**Phase A: Baseline (R16).** Rebase `feat/unified-recipes` onto `main`
(5cc03f0) and copy the spec artifacts into the worktree. Run the suite to get
a green baseline:

`.venv\Scripts\python -m pytest -q -m "not requires_flex"`

**Phase B: Format and loader (FR-001..006, FR-040, FR-041, FR-045).** Build
`recipe_files.py`, the packaging edits, the loader merge, the validator
extensions (including the index-driven deprecation check and the raw-LCM gate), and one seed recipe file (`parser-coverage`) to exercise the path
end to end.

**Phase C: Local recipes (FR-010..016).** Build `local_recipes.py`, rewire
the capture in `execution.py`, write the migration, and port the tests.

**Phase D: Search and tools (FR-020..027).** Build the ranker, the search and
find_examples keys, `list_recipes`, the `list_skeletons` alias, the
instructions, the key registry, the contract snapshot, and the golden fixture.

**Phase E: Promotion (FR-030..032).** Build the CLI and the extract_patterns
wording.

**Phase F: Recipe batch (FR-050..053, FR-042..045).** Port the 16 targets one
file at a time: validator green (including the FR-045 raw-LCM gate, so every
raw-LCM line is either replaced by its flexicon wrapper or annotated), then
Sena 3 evidence, then `verified_against` and `raw_lcm_lines` set. Each port also updates `raw-lcm-ledger.md`: rewrite rows it relied on
move to `confirmed`, and any gap it keeps must have a filed flexicon issue
number (no `TODO-file` rows may remain for a shipped recipe). Live writes need a human present (R14). Recipes blocked on a flexicon gap
either ship with the raw-LCM fallback plus an issue comment, or are deferred.
The phase needs at least 12 of the 16.

**Phase G: Docs, index, release notes (FR-060).** Update the docs, run a
full refresh to regenerate `common_patterns`, and write the CHANGELOG entries.
Finish with `scripts/validate_integrity.py server` and pre-commit.

Phases B through E are independent of Phase F, apart from the seed recipe.
Phase F can start once Phase B lands.

## Pattern audit obligation

`_entities_used_in_session` tags captured code with the *session's* API list
instead of the code's own. That is a shaped bug: provenance taken from the
ambient session instead of the artifact. The PR body must carry a pattern-audit
section (use the `sweep-pattern` skill) listing other places that attribute
session-wide `discovered_apis` / `validated_apis` to a single artifact. Two
known candidates to check are the `op_telemetry` `auto_discovered` fields and
the `extract_patterns` mining evidence.

## Live-LCM verification obligation

Phase F write recipes: every recipe gets a dry run. Recipes that create or
delete objects also get a live write on Sena 3 using `zzRecipeTest`-prefixed
objects, with pre/post values, cleanup, and `.fwdata` hash and mtime recorded
(R14). This is the evidence the `after_implement` lex-verification hook
requires. A run with no human present stops at `needs-human`. Verification runs on Sena 3 only, never on Claude-Swahili (the work project).

## Risks

- **flexicon gaps** may force raw-LCM fallbacks. #542-#547 already shipped
  in flexicon 4.11.0, so recipes use those APIs, but the ledger's remaining
  gap rows (for example `phon_rules`, which has no flexicon surface at all)
  still need raw LCM. These are allowed with an issue comment and
  must pass the validator. The fallback is to defer the recipe (FR-052).
- **Ranking regressions on existing queries.** Mitigated by keeping the old
  attachment function separate (R10) and by the frozen-dict test.
- **Parse worker rewriting `.fwdata`** during verification. Mitigated by
  recording hash and mtime on every run, not only writes.
- **mcp 1.x vs 2.x `instructions` kwarg.** Covered by
  `test_server_instructions.py` under whichever mcp is installed. The canary
  job covers the other major.
