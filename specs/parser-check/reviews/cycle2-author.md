## (1) Placement: SPLIT — read-only facade in flexicon, write path stays in the MCP

**Recommendation:** a thin `project.Parser` facade (`TryWord`, `ParseWord`, `TraceWord` — names TBD to flexicon's own verb conventions) wrapping `HCParser(cache)` ships in **flexicon**. Filing (`ParseFiler`/`ProcessParse`), the confirmation/backup ladder, and the whole confidence-gradient orchestration (diff, sandbox export, caching) stay in **FlexToolsMCP**.

**Why the split, not a side:**

- Flexicon already touches parser-adjacent data — `Agents.GetParserAgents()` returns `ICmAgent` parser agents (confirmed live in `flexicon_api_v4.8.0.json` line ~2358-2386) — so a `Parser` facade isn't a foreign category, it's an adjacent one. Flexicon's category list (`grammar`, `lexicon`, `texts`, `notebook`, `lists`, `system`, `discourse`, `reversal`, `scripture`, `general` — no `parser`/`engine` category exists) confirms this would be a genuinely new category, not a natural extension of an existing one — a real cost, but a bounded one.
- **The stated MCP purpose is decisive for the read half.** `CLAUDE.md`'s Project Overview says FLExTools MCP exists to help generate FlexTools modules, and every generated module explicitly imports `from flexicon import (...)` — never from MCP server internals. If `TryWord` lives only in MCP server code, a generated module (or any FlexTools/FlexTrans script run outside the MCP entirely) cannot call it. That is a direct contradiction of the project's own stated purpose, not a style preference.
- **The dependency-light/heavy asymmetry cycle 1 found is the deciding argument, and it cuts by spine, not by side.** The read path never loads xCore/WinForms and needs no stubs (cycle1-programmer Q4b) — it's exactly the shape flexicon already wraps (cache-derived, no UI). The write path needs a null `PropertyTable`, a stub `IdleQueue`, a synchronous `UpdateWordforms` call, and sits inside a `NonUndoableUnitOfWorkHelper` block that can delete never-reviewed analyses (cycle1-programmer/domain both). That's not an "operate on this domain object" shape (flexicon's CRUD idiom) — it's a "run a vetted, gated procedure with irreversible side effects," which is exactly what FlexToolsMCP's `confirmed=True` + backup-before-write ladder (`run_module`, `tool_definitions.py:299-314`) already exists to own. Flexicon has a `writeEnabled` check but no backup/confirmation ladder of its own; building one there duplicates machinery the MCP already has.
- Cross-repo cost is real (against-argument) but bounded: only `ParserCore.dll` + `SIL.Machine.Morphology.HermitCrab*` assemblies are added to flexicon's footprint for the read half, not the xCore-referencing write apparatus.

**What would change this:** if flexicon's own maintainers (not visible from this staged scope) reject adding any FieldWorks-parser-assembly dependency at all — that's a cross-repo negotiation I can't resolve from here, only flag. Also, if the third spine (sandbox) turns out to need zero cache access even for read-only trial parses, that narrows how much flexicon-side surface is worth building, but doesn't flip the recommendation, since `HCParser(cache)` is in-process by definition.

## (2) The capability-split override: AGREE, with one addition

The lead's split holds up against repo convention, and my cycle-1 "never understate" principle was solving the wrong axis. `tool_definitions.py` shows the house rule: annotations are a **per-tool** declaration of that tool's own maximum reachable capability, evaluated before any argument is known — `READ_ONLY_SAFE` covers unconditionally-read tools, while `run_module` alone gets `readOnlyHint=False/destructiveHint=True` because *that tool's own code path* can reach a write depending on `write_enabled`/`confirmed`. Cycle1-programmer Q4b proved, from source, that `flextools_try_word`'s call path structurally cannot reach `ParseFiler`/xCore — so under the house rule it earns `READ_ONLY_SAFE` on its own facts, the same way `get_object_api` does. My original single-tool design was solving "don't understate within one fused tool with an `apply` flag"; the lead moved the boundary to the tool itself, which is what static MCP annotations are actually for. Tagging `try_word` destructive would *overstate*, and for a maintainer-stated safety feature ("tests in an export... live changes for confident changes"), overstating throttles the very low-friction hypothesis-testing loop the gradient exists to enable.

One addition: `flextools_parse_text`'s `apply=false` default should reuse `run_module`'s existing WRITE-PATH SAFETY LADDER verbatim (`confirmed=True` + backup-before-write) rather than invent a parallel gate — simplicity/consistency, and it's the one place cycle 1 flagged real destructive risk (deleting never-reviewed analyses).

**Third spine — sandbox.** Add a distinctly-named tool, e.g. `flextools_parse_sandbox`, `READ_ONLY_SAFE` with respect to the live database (it never opens the live `.fwdata` for write — matches SPEC.md's existing S6/hcparse.ps1 mechanism), but its risk register is disk/subprocess (project copy, `dotnet` timeout), already covered by SPEC.md §12, not the LCM write surface at all.

**Telling the three apart:** don't rely on annotation bits alone — most clients surface `readOnlyHint`/`destructiveHint` as icons or gates, not prose a calling LLM reads at decision time. Follow the `run_module` pattern of stating it in the description's first line: `try_word` = "in-process, live DB, read-only, cannot add analyses"; `parse_text` = "in-process, live DB, WRITES on apply=True, non-undoable, ladder-gated"; `parse_sandbox` = "exported/copied grammar, never touches the live DB, speculative edits welcome." Name the spine, don't make the caller infer it.

## (3) XAmple non-goal: DEFER, not drop, not keep silently

SPEC.md §15's blanket "out of scope" predates cycle 1's finding that `IParser`-level support is near-free except for one genuinely open gap (`dataDir`/`XAmpleParser.cs` unread, per cycle1-programmer Q3). The honest content of the non-goal has changed even though the bottom-line scope hasn't — flag it as stale prose, not settled fact.

**Non-negotiable regardless of the defer/keep decision:** every parse tool must read `LanguageProject.MorphologicalDataOA.ActiveParser` before running, and **refuse**, not silently substitute, when the project is configured for `"XAmple"` and the tool only implements HC — mirroring `ParserWorker.cs`'s own `default: throw InvalidOperationException` (cycle1-programmer Q2). SPEC.md §8.3 already states the house principle for trace fabrication ("a confident wrong answer... would be worse than useless"); parsing with the wrong engine and reporting results as if they reflect the project's actual configured parser is the same violation one layer up, not a scope choice. Concretely: a new `parser_engine_mismatch` error code (`configured_engine`, `supported_engines`, hint) is a one-field-read, cheap enough to ship at CP1 independent of whether XAmple support ever lands.
